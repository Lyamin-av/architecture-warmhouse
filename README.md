# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- В коде монолита функциональность управления отоплением отсутствует: нет эндпоинтов и интеграций для модулей отопления. Не считаю верным вписывать сюда информацию из описания задания.

**Мониторинг температуры:**

- Пользователи (любые клиенты API, так как нет аутентификации и разграничения доступа) могут:
  - получить список всех зарегистрированных датчиков — `GET /api/v1/sensors`;
  - получить датчик по идентификатору — `GET /api/v1/sensors/{id}`;
  - зарегистрировать новый датчик (обязательны `name`, `type`, `location`, опционально `unit`) — `POST /api/v1/sensors`;
  - изменить параметры датчика — `PUT /api/v1/sensors/{id}`;
  - удалить датчик — `DELETE /api/v1/sensors/{id}`;
  - вручную обновить текущее значение и статус датчика — `PATCH /api/v1/sensors/{id}/value`;
  - получить температуру по названию локации (значение, единица измерения, статус, метка времени, описание) — `GET /api/v1/sensors/temperature/{location}`.
- Система поддерживает:
  - хранение датчиков и их последних значений в PostgreSQL (одна таблица `sensors`);
  - запрос температуры по локации напрямую во внешний сервис, без обращения к БД и по id с запросом во внешний сервис.

### 2. Анализ архитектуры монолитного приложения

1. Язык: Go.
   - HTTP-фреймворк — Gin (gin-gonic/gin v1.8.2);
   - драйвер БД — pgx/v5.
2. База данных: PostgreSQL.
   - одна база smarthome;
   - строка подключения берётся из DATABASE_URL;
   - SQL-запросы ручные в db/db.go.
3. Архитектура: монолит, один бинарник, который содержит:
   - handlers — как HTTP-слой;
   - services — как HTTP-клиент к temperature-api (может и можно к бизнес-логике отнести, но нет);
   - db — для доступа к PostgreSQL;
   - models — это структуры данных.

   Внешняя зависимость: temperature-api — отдельный процесс, монолит обращается к нему по HTTP.
4. Взаимодействие: синхронное. Входящие запросы обрабатываются параллельно; внутри запроса списка датчиков внешний сервис вызывается последовательно для каждого датчика.
5. Масштабируемость: ограничена, так как монолит сложно масштабировать по частям. Но, так как состояние приложение хранит только в PostgreSQL, поэтому теоретически его можно масштабировать горизонтально целиком, запустив несколько копий и подключив балансировщик на входе. Но никакие функции отдельно масштабировать нельзя.
6. Развёртывание: требует остановки всего приложения, любое изменение требует пересборки и перезапуска всего бинарника, т.е. отдельно сделать мини-релиз и выкатить отдельную функцию не получится.
7. Нет аутентификации и авторизации.
8. Соответствие между датчиками в БД и во внешнем сервисе держится только на совпадении автоинкрементного ID. Это криво, так быть не должно.

- Охрана [supporting]
    - Контекст: Управление охраной (ссылается на дом и зоны плана,
      в т. ч. периметр; хранит состояние и режим охраны)

        - режимы охраны;

        - распознавание номеров;
        - слежение за объектом.

- Управление телематикой [supporting]
    - Контекст: Управление приборами (хозяин прибора: прибор существует
      в системе с момента сопряжения; идентификатор присваивается
      при сопряжении). Операции:
        - сопряжение (подключение новых приборов);
        - настройка приборов (технические параметры конкретного прибора:
          частота опроса, адрес, калибровка);
        - передача команд на приборы (единственный путь команд к приборам);
        - контроль работоспособности приборов.
    - Контекст: Телеметрия (единственный контекст, обращающийся к приборам
      за показаниями). Операции:
        - плановый опрос с заданной частотой;
        - внеочередной опрос по запросу;
        - хранение истории показаний в архиве;
        - выдача текущих и исторических показаний (пользователю,
          сценариям, отоплению).

- Интеграция приборов [core]
    - Контекст: Адаптеры протоколов [ACL] (перевод стандартных протоколов
      партнёров в единую внутреннюю модель показаний и команд;
      «Телеметрия» и «Передача команд на приборы» работают
      с приборами через адаптеры)
    - Контекст: Каталог типов приборов (описание типа как данных:

      новый тип добавляется записью в каталог без изменения кода;
      прибор неизвестного типа подключается как универсальный —
      значение + единица измерения)

- Пользователи [generic]
    - Контекст: Регистрация пользователей в системе (владеет профилем
      пользователя: имя, контакты, настройки; при регистрации создаёт
      учётные данные в «Аутентификации» — Conformist; идентификатор
      пользователя общий с «Аутентификацией»)
    - Контекст: Настройка ролевой модели (права и видимость в соответствии
      с планом дома; хранит связь «пользователь — дом — роль» и ссылки
      на дом и зоны плана; пользователей берёт из «Регистрации»)

- Аутентификация [generic]
    - Контекст: Поддержка различных режимов аутентификации (владеет
      учётными данными и проверяет, кто вошёл; на выходе — подтверждённая
      личность с идентификатором пользователя; типовая задача, берётся
      готовое решение)

- Автоматизация [core]
    - Контекст: Конструктор сценариев (настройка сценариев работы; это же —
      программирование системы покупателем; приборы и зоны для сценария
      берёт из «Конструктора дома», возможности приборов — показания
      для условий и команды для действий — из «Каталога типов приборов»)
    - Контекст: Выполнение сценариев (хранит активные сценарии, непрерывно
      проверяет условия и отдаёт команды через контексты типов приборов;
      отделено от конструктора из-за разного характера работы: конструирование
      редкое, выполнение непрерывное). Условия сценариев:
        - показания приборов — от «Телеметрии»;
        - состояние приборов — от «Управления приборами»;
        - события охраны (тревога, постановка, снятие) — от «Управления охраной»;
        - время и расписание, ручной запуск пользователем — внутренние.
      Пример действия: постановка на охрану.

- Конструктор дома [supporting]
    - Контекст: Зонирование и расстановка приборов на плане дома/участка
      (хозяин понятий «дом», «зона» и «периметр» — периметр является
      зоной на плане; хранит ссылку на прибор по идентификатору, его
      место и зону и признак «распределён / не распределён»;
      нераспределённые приборы показываются в блоке интерфейса
      «Новые приборы»; о новых и удалённых приборах узнаёт
      от «Управления приборами»)

**Типы поддоменов:** (мне понравилось решение делить поддомены по типам)
- core — Автоматизация, Интеграция приборов: отличие от конкурентов —
  пользователь сам программирует систему, к экосистеме подключаются
  приборы любых партнёров, включая неизвестные;
- supporting — управление отоплением, освещением, воротами,
  видеонаблюдением, Охрана, Управление телематикой, Конструктор дома;
- generic — Пользователи, Аутентификация.

**Словарь:**
- Прибор — любое устройство, подключённое к системе («устройство»
  в требованиях).
- Датчик — прибор, который только измеряет (sensor в монолите).
- Исполнительное устройство — прибор, выполняющий команды: котёл,
  лампа, привод ворот, камера.
- Модуль управления — прибор-шлюз (хаб), через который подключаются
  другие приборы; сопрягается как обычный прибор.
- Телеметрия — показания приборов (значение, единица измерения, время,
  прибор) и их история. Ими владеет контекст «Телеметрия»: он собирает
  показания с заданной частотой или внеочередно, ведёт архив и выдаёт
  текущие и исторические значения.

**Правила:**
- прибор существует с момента сопряжения, хозяин —
  «Управление приборами»; остальные контексты ссылаются на прибор
  по идентификатору, выданному при сопряжении.
- хозяин дома, зон и периметра — «Конструктор дома».
  Пользователь сначала регистрируется, затем создаёт дом и становится
  его владельцем. «Пользователи» и «Управление охраной» ссылаются
  на дом и зоны по идентификатору и хранят только своё.
- пользователь, «Автоматизация» и «Управление охраной»
  управляют приборами через контексты своего типа (отопление, освещение,
  ворота, камеры); те передают команды через «Передачу команд на приборы».
- показания приборов идут только через «Телеметрию».
  Исключение: видеопоток «Видеонаблюдение» получает с камер само,
  поскольку это непрерывный поток большого объёма, а не дискретные
  показания, и он не укладывается в модель телеметрии.
- «Телеметрия», «Управление приборами» и «Управление охраной»
  публикуют события в едином формате (Open Host Service / Published
  Language); «Выполнение сценариев» на них подписывается.
- аутентификация сквозная — проверяется на входе в систему. Пользовательские контексты проверяют права
  и видимость зон по «Настройке ролевой модели».

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Get All Sensors
