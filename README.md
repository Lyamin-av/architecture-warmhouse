# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- В коде монолита функциональность управления отоплением отсутствует: нет эндпоинтов и интеграций для модулей отопления. Не считаю верным вписывать сюда информацию из описания задания.

**Мониторинг температуры:**

- Пользователи (любые клиенты API, так как нет аутентификации и разграничения доступа) могут:
  - получить список всех зарегистрированных датчиков — `GET /api/v1/sensors`;
  - получить датчик по идентификатору — `GET /api/v1/sensors/{id}`;
  - зарегистрировать новый датчик (обязательны `name`, `type`, `location`, опционально `unit`) — `POST /api/v1/sensors`;
  - изменить параметры датчика — `PUT /api/v1/sensors/{id}`;
  - удалить датчик — `DELETE /api/v1/sensors/{id}`;
  - вручную обновить текущее значение и статус датчика — `PATCH /api/v1/sensors/{id}/value`;
  - получить температуру по названию локации (значение, единица измерения, статус, метка времени, описание) — `GET /api/v1/sensors/temperature/{location}`.
- Система поддерживает:
  - хранение датчиков и их последних значений в PostgreSQL (одна таблица `sensors`);
  - запрос температуры по локации напрямую во внешний сервис, без обращения к БД и по id с запросом во внешний сервис.

### 2. Анализ архитектуры монолитного приложения

1. Язык: Go.
   - HTTP-фреймворк — Gin (gin-gonic/gin v1.8.2);
   - драйвер БД — pgx/v5.
2. База данных: PostgreSQL.
   - одна база smarthome;
   - строка подключения берётся из DATABASE_URL;
   - SQL-запросы ручные в db/db.go.
3. Архитектура: монолит, один бинарник, который содержит:
   - handlers — как HTTP-слой;
   - services — как HTTP-клиент к temperature-api (может и можно к бизнес-логике отнести, но нет);
   - db — для доступа к PostgreSQL;
   - models — это структуры данных.

   Внешняя зависимость: temperature-api — отдельный процесс, монолит обращается к нему по HTTP.
4. Взаимодействие: синхронное. Входящие запросы обрабатываются параллельно; внутри запроса списка датчиков внешний сервис вызывается последовательно для каждого датчика.
5. Масштабируемость: ограничена, так как монолит сложно масштабировать по частям. Но, так как состояние приложение хранит только в PostgreSQL, поэтому теоретически его можно масштабировать горизонтально целиком, запустив несколько копий и подключив балансировщик на входе. Но никакие функции отдельно масштабировать нельзя.
6. Развёртывание: требует остановки всего приложения, любое изменение требует пересборки и перезапуска всего бинарника, т.е. отдельно сделать мини-релиз и выкатить отдельную функцию не получится.
7. Нет аутентификации и авторизации.
8. Соответствие между датчиками в БД и во внешнем сервисе держится только на совпадении автоинкрементного ID. Это криво, так быть не должно.

- Управление воротами [supporting]
    - Контекст: Управление воротами

- Управление видеонаблюдением [supporting]

      постоянно, для распознавания номеров; с камер периметра — пока дом

    - Контекст: Управление камерами (команды камерам, в т. ч. слежение

- Охрана [supporting]
    - Контекст: Управление охраной (ссылается на дом и зоны плана,

        - постановка на охрану и снятие с охраны дома и периметра;
        - режимы охраны;
        - журнал тревог; тревога поднимается при срабатывании датчика
          в зоне под охраной (показания и состояние приборов — через брокер

        - запуск и остановка потока на анализ: с камеры у ворот — постоянно,
          с камер периметра — при постановке и снятии с охраны;
        - открытие ворот для автомобиля с номером из перечня
          (через «Управление воротами») — только когда дом не на охране;
          под охраной ворота по номеру автоматически не открываются.
    - Контекст: Видеоаналитика [generic внутри supporting] (поток с камер

        - слежение за объектом.

      в системе с момента сопряжения; идентификатор присваивается
      при сопряжении). Операции:
        - сопряжение (подключение новых приборов);
        - настройка приборов (технические параметры конкретного прибора:
          частота опроса, адрес, калибровка);
        - передача команд на приборы (единственный путь команд к приборам);
        - контроль работоспособности приборов.
    - Контекст: Телеметрия (единственный контекст, обращающийся к приборам
      за показаниями). Операции:
        - плановый опрос с заданной частотой;
        - внеочередной опрос по запросу;
        - хранение истории показаний в архиве;
        - выдача текущих и исторических показаний (пользователю,
          сценариям, отоплению, охране).

- Интеграция приборов [core]
    - Контекст: Адаптеры протоколов [ACL] (перевод стандартных протоколов
      партнёров в единую внутреннюю модель показаний и команд;
      «Телеметрия» и «Передача команд на приборы» работают
      с приборами через адаптеры)
    - Контекст: Каталог моделей приборов (описание модели как данных:
      категория и вид прибора, что прибор измеряет, в каких единицах,
      какие команды принимает; единая модель команд категории и
      соответствие ей команд модели;
      новая модель добавляется записью в каталог без изменения кода;
      прибор неизвестной модели подключается как универсальный —
      значение + единица измерения)

- Пользователи [generic]
    - Контекст: Регистрация пользователей в системе (владеет профилем
      пользователя: имя, контакты (логин — почта или имя — и почта
      принадлежат «Пользователям»); при регистрации создаёт учётные данные
      в «Аутентификации», передавая логин и почту, и так же сообщает ей
      о смене логина или почты — Conformist; идентификатор пользователя
      общий с «Аутентификацией»)
    - Контекст: Настройка ролевой модели (роли, права и связь
      «пользователь — дом — роль»; хранит ссылки на дом и зоны плана,
      которые запрашивает у «Конструктора дома»; пользователей берёт
      из «Регистрации». Роли преднастроенные (Владелец, Администратор
      и др.) и созданные владельцем для своего дома; у пользователя
      в доме одна роль. Права роли на приборы задаются в зоне
      по категории приборов, пустая зона или категория — «все»;
      системные права (приглашать пользователей, менять план,
      сопрягать приборы, редактировать сценарии) есть только
      у Владельца и Администратора; видимость зон следует из прав. «Администратор» —
      служебная роль: дом создаёт Администратор (например, монтажник),
      о создании дома «Конструктор дома» сообщает событием, и создатель
      получает в этом доме роль «Администратор»; затем Администратор
      назначает зарегистрированному пользователю роль «Владелец»;
      Владелец может снять Администратора со своего дома)

- Аутентификация [generic]
    - Контекст: Поддержка различных режимов аутентификации (владеет
      учётными данными и проверяет, кто вошёл; хранит копию логина и почты
      для входа и сброса пароля по почте — источник истины остаётся
      у «Пользователей»; на выходе — подтверждённая личность
      с идентификатором пользователя; типовая задача, берётся готовое
      решение)

- Автоматизация [core]
    - Контекст: Конструктор сценариев (настройка сценариев работы; это же —
      программирование системы покупателем; приборы и зоны для сценария
      берёт из «Конструктора дома», возможности приборов — показания
      для условий и команды для действий — из «Каталога моделей приборов»)
    - Контекст: Выполнение сценариев (хранит активные сценарии, непрерывно
      проверяет условия и отдаёт команды через контексты категорий приборов;
      отделено от конструктора из-за разного характера работы: конструирование
      редкое, выполнение непрерывное). Сценарий: при [триггер] если
      [условие] то [действия].
      Триггеры — когда проверять сценарий:
        - показания приборов — от «Телеметрии»;
        - состояние приборов — от «Управления приборами»;
        - события охраны (тревога, постановка, снятие) — от «Управления охраной»;
        - время и расписание, ручной запуск пользователем — внутренние.
      Условия — проверка текущего состояния дома (необязательны,
      комбинируются через И / ИЛИ): последние показания и состояния
      приборов, режим охраны, интервал времени; текущее состояние
      «Выполнение сценариев» хранит само и обновляет по каждому событию.
      Все триггеры, включая ручной запуск, проходят одинаковую проверку
      условий.
      Примеры действий: постановка на охрану, отправка уведомления
      (через «Рассылку уведомлений»).

- Конструктор дома [supporting]
    - Контекст: Зонирование и расстановка приборов на плане дома/участка
      (хозяин понятий «дом», «зона» и «периметр» — периметр является
      зоной на плане; хранит ссылку на прибор по идентификатору, его
      место и зону и признак «распределён / не распределён»;
      нераспределённые приборы показываются в блоке интерфейса
      «Новые приборы»; о новых, удалённых и восстановленных приборах
      узнаёт от «Управления приборами»; прибор и зона удаляются мягко:
      помечаются как удалённые, исчезают с плана дома и из связей,
      но хранят историческую информацию, и их можно восстановить;
      об удалении и восстановлении зоны «Конструктор дома» публикует
      события, на которые подписаны «Пользователи», «Охрана»,
      «Отопление», «Видеонаблюдение» и «Автоматизация»; о создании
      дома — событие, на которое подписаны «Пользователи»)

- Уведомления [generic]
    - Контекст: Рассылка уведомлений (получает события от «Управления
      охраной», «Управления приборами» (только состояние приборов,
      например «датчик потерял связь», без показаний) и «Выполнения
      сценариев»; определяет
      получателей по дому и ролям — из «Настройки ролевой модели», их
      контакты — из «Регистрации пользователей»; владеет настройками
      уведомлений пользователя (каналы, типы событий) и хранит их
      по идентификатору пользователя; доставку выполняет внешний сервис
      уведомлений — push, SMS, email)

**Типы поддоменов:** (мне понравилось решение делить поддомены по типам)
- core — Автоматизация, Интеграция приборов: отличие от конкурентов —
  пользователь сам программирует систему, к экосистеме подключаются
  приборы любых партнёров, включая неизвестные;
- supporting — управление отоплением, освещением, воротами,
  видеонаблюдением, Охрана, Управление телематикой, Конструктор дома;
- generic — Пользователи, Аутентификация, Уведомления.

**Словарь:**
- Прибор — любое устройство, подключённое к системе («устройство»
  в требованиях).
- Датчик — прибор, который только измеряет (sensor в монолите).
- Исполнительное устройство — прибор, выполняющий команды: котёл,
  лампа, привод ворот, камера.
- Модуль управления — прибор-шлюз (хаб), через который подключаются
  другие приборы; сопрягается как обычный прибор.
- Вид прибора — датчик, исполнительное устройство или модуль управления.
- Модель прибора — конкретная модель партнёра (например, «Bosch Condens 2300»):
  протокол, команды, единицы измерения. Моделей много, их добавляют партнёры.
- Категория прибора — назначение прибора: отопление, свет, ворота, камеры.
  Категорий немного; в одной категории много моделей.
- Телеметрия — показания приборов (значение, единица измерения, время,
  прибор) и их история. Ими владеет контекст «Телеметрия»: он собирает
  показания с заданной частотой или внеочередно, ведёт архив и выдаёт
  текущие и исторические значения.

**Правила:**
- прибор существует с момента сопряжения, хозяин —
  «Управление приборами»; остальные контексты ссылаются на прибор
  по идентификатору, выданному при сопряжении.
- хозяин дома, зон и периметра — «Конструктор дома».
  Дом создаёт Администратор (служебная роль), затем назначает
  зарегистрированному пользователю роль «Владелец». «Пользователи»
  и «Управление охраной» ссылаются на дом и зоны по идентификатору и хранят только своё.
- пользователь, «Автоматизация» и «Управление охраной»
  управляют приборами через контексты своей категории (отопление, освещение,
  ворота, камеры); те передают команды через «Передачу команд на приборы».
- показания приборов идут только через «Телеметрию».
  Исключение: видеопоток «Видеонаблюдение» получает с камер само,
  поскольку это непрерывный поток большого объёма, а не дискретные
  показания, и он не укладывается в модель телеметрии.
- «Телеметрия», «Управление приборами» и «Управление охраной»
  публикуют события в едином формате (Open Host Service / Published
  Language); «Выполнение сценариев» на них подписывается,
  «Настройка температурного режима» — на показания приборов,
  «Управление охраной» — на показания и состояние приборов.
- команды приборам асинхронные: «Передача команд на приборы» ведёт журнал
  команд и публикует «результат команды» (выполнена / ошибка / таймаут);
  контексты категорий подводят по нему итог своего действия.
- цепочка вызовов и событий несёт сквозной идентификатор (correlationId),
  по нему «Выполнение сценариев» сопоставляет итоги действий с выполнением сценария.
- категория и вид прибора передаются в событии «новый прибор»
  и хранятся копией в «Конструкторе дома» — без цепочки запросов
  во время работы.
- аутентификация сквозная — проверяется на входе в систему. Пользовательские контексты проверяют права
  и видимость зон по «Настройке ролевой модели».

**За границей системы:** выбор и покупка модулей и комплектов.

### **4. Проблемы монолитного решения**

1. Нет аутентификации и авторизации: любой клиент API видит и изменяет все датчики.
2. Для добавления нового типа прибора необходимо править код: тип `temperature` зашит в модель и отдельно обрабатывается в обработчиках.
3. Единственный источник данных — `temperature-api`, он жёстко прописан в коде; подключить приборы других производителей и протоколов нельзя.
4. Пользователи не могут программировать систему: сценариев управления нет, как нет и управления приборами вообще — только чтение показаний.
5. Архива измерений нет: в БД хранится только последнее значение датчика, и попадает оно туда только при ручном вызове `PATCH /sensors/{id}/value`. Значения, полученные от `temperature-api` при чтении, в БД не сохраняются.
6. Чтение синхронное и последовательное: при запросе списка датчиков монолит по очереди обращается к `temperature-api` за каждым температурным датчиком (таймаут — 10 секунд на вызов), поэтому время ответа растёт с числом датчиков и зависит от доступности внешнего сервиса.
7. Данные с приборов появляются, только когда клиент что-то читает: приборы сами ничего не присылают, событий нет.
8. Масштабирование ограничено: приложение можно масштабировать только целиком, запуская несколько копий, а отдельные функции (например, чтение телеметрии) — нет. Все копии работают с одной базой PostgreSQL и одним `temperature-api`, которые становятся узким местом; в текущей конфигурации (`docker-compose.yml`) запущен один контейнер без балансировщика.

# Задание 3. Разработка ER-диаграммы

ER-диаграмма To-Be системы на логическом уровне, нотация «воронья лапка».
У каждого микросервиса своя БД (database per service), поэтому сущности
сгруппированы по базам: 9 баз, у «Освещения», «Ворот» и «Видеонаблюдения»
своей БД нет.

![ER-диаграмма](diagrams/er/er-diagram.png)

Исходник: [er-diagram.puml](diagrams/er/er-diagram.puml)

**Обозначения:**
- жирная сплошная линия — внешний ключ (FK) внутри одной БД;
- серый пунктир — логическая ссылка на сущность в БД другого сервиса:
  FK между базами нет, хранится только идентификатор; целостность
  поддерживается событиями (мягкое удаление и восстановление приборов
  и зон);
- `<<ext: Сервис>>` — атрибут-ссылка на сущность в БД другого сервиса;
- концы линий: `||` — ровно один, `o|` — ноль или один,
  `}|` — один или много, `}o` — ноль или много;
- `*` — обязательный атрибут.

**Ключевые решения:**
- идентификатор прибора выдаётся при сопряжении в «Телематике» и общий
  для всех баз; идентификатор пользователя общий для «Пользователей»
  и «Аутентификации»;
- у дома несколько планов (этажи, участок), зона лежит на одном плане,
  периметр — зона на плане участка; прибор на плане — ссылка на план
  и координаты; хаб — ссылка прибора на прибор;
- ролевая модель: роли преднастроенные (Владелец, Администратор и др.)
  и свои роли дома, у пользователя в доме одна роль; права на приборы
  задаются в зоне по категории приборов (пустая зона или категория —
  «все»), системные права — отдельно; видимость зон следует из прав;
  владелец дома — назначение роли «Владелец»;
- категории приборов (свет, отопление, ворота, камеры и др.) — справочник
  в «Интеграции приборов», на него ссылаются модели приборов и права ролей;
  у категории — единая модель команд («Команда категории»), команды модели
  ссылаются на неё;
- категория и вид прибора копируются в «Прибор на плане» из события
  «новый прибор» (Конфигурация дома выдаёт приборы зоны с фильтром);
- «Телематика» ведёт журнал команд: инициатор, correlationId, статус
  (отправлена, выполнена, ошибка, таймаут);
- состояние охраны хранится отдельно для дома и для периметра;
- сценарий создаётся из шаблона; шаблоны преднастроенные и пользовательские
  (общие для дома); условия группируются И/ИЛИ через ссылку на родительское
  условие;
- «Автоматизация» хранит проекции состояния приборов и охраны,
  обновляемые по событиям;
- отправленное уведомление — запись на каждого получателя и канал
  со статусом доставки.

# Задание 4. Создание и документирование API

### 1. Тип API

Будем использовать:

- **REST (HTTP/JSON)** — для запросов, когда нужен ответ сразу. Это клиенты, которые работают через API Gateway, и сервисы. Эти сущности (дома, зоны, приборы, роли, сценарии) удобно описывать как ресурсы. HTTP понимают все клиенты и шлюз. Нагрузка небольшая. Документация — OpenAPI.
- **События через RabbitMQ** — для оповещений. Это показания, тревоги, новые приборы и т. п. Отправитель не знает получателей, одно событие получают сразу несколько сервисов, и оно не теряется, если получатель временно недоступен. Документация — AsyncAPI.

### 2. Документация API

Спроектирована одна сквозная цепочка — «установить температуру в зоне»
(MVP, отопление). Четыре эндпоинта, четыре микросервиса, спецификации
OpenAPI 3.0 по файлу на сервис. Ссылка «Swagger UI» открывает интерактивную
документацию прямо из репозитория (для правки — [Swagger Editor](https://editor.swagger.io/)):

| # | Сервис | Эндпоинт | Кто вызывает | Ответ | Спецификация |
|---|---|---|---|---|---|
| 1 | Управление отоплением | `PUT /zones/{zoneId}/temperature-mode` — задать режим зоны (температура + режим) | API Gateway, Автоматизация | `200` режим сохранён | [heating.yaml](api/heating.yaml) · [Swagger UI](https://petstore.swagger.io/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/heating.yaml) |
| 2 | Конфигурация дома | `GET /zones/{zoneId}/devices?category=&kind=` — приборы зоны | Отопление | `200` список приборов | [house-configuration.yaml](api/house-configuration.yaml) · [Swagger UI](https://petstore.swagger.io/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/house-configuration.yaml) |
| 3 | Телематика | `POST /devices/{deviceId}/commands` — команда прибору | Отопление (и Освещение, Ворота, Видеонаблюдение) | `202` команда принята | [telematics.yaml](api/telematics.yaml) · [Swagger UI](https://petstore.swagger.io/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/telematics.yaml) |
| 4 | Интеграция приборов | `POST /commands` — команда через адаптер протокола | Телематика | `202` передано адаптеру | [device-integration.yaml](api/device-integration.yaml) · [Swagger UI](https://petstore.swagger.io/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/device-integration.yaml) |

*Дальше.* Телематика по расписанию опрашивает датчик `d-103` и публикует
`device.readings`; по показаниям Отопление следит, прогревается ли зона.

**Итог.** Синхронных вызовов два — сохранить режим (№ 1) и получить приборы зоны (№ 2).
Работа с приборами асинхронная: вызов отвечает `202`, результат приходит событием.
`X-Correlation-Id` / `correlationId` связывает все вызовы и события в одну цепочку.

**События цепочки** — AsyncAPI 2.6, по файлу на публикующий сервис
(ссылка «AsyncAPI Studio» открывает интерактивную документацию). Команды асинхронные,
поэтому результат вызовов № 3–4 приходит этими событиями:

| Событие (канал) | Публикует | Подписчики | Спецификация |
|---|---|---|---|
| `device.added` — новый прибор с моделью, категорией и видом | Телематика | Конфигурация дома | [telematics-events.yaml](api/telematics-events.yaml) · [AsyncAPI Studio](https://studio.asyncapi.com/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/telematics-events.yaml) |
| `device.readings` — показания (плановый и внеочередной опрос) | Телематика | Отопление, Охрана, Автоматизация | [telematics-events.yaml](api/telematics-events.yaml) · [AsyncAPI Studio](https://studio.asyncapi.com/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/telematics-events.yaml) |
| `device.command-result` — результат команды (выполнена / ошибка / таймаут) | Телематика | Отопление, Освещение, Ворота, Видеонаблюдение, Уведомления | [telematics-events.yaml](api/telematics-events.yaml) · [AsyncAPI Studio](https://studio.asyncapi.com/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/telematics-events.yaml) |

| `temperature-mode.result` — режим применён / не применён | Отопление | Автоматизация | [heating-events.yaml](api/heating-events.yaml) · [AsyncAPI Studio](https://studio.asyncapi.com/?url=https://raw.githubusercontent.com/Lyamin-av/architecture-warmhouse/warmhouse/api/heating-events.yaml) |

**Контракты:**
- команды асинхронные: ответ `202`, результат приходит событием
  через брокер — «показания», «результат команды от адаптера» (Интеграция → Телематика),
  «результат команды» (Телематика → сервисы категорий и Уведомления),
  итоговое «режим применён / не применён» (Отопление → Автоматизация);
- заголовок `X-Correlation-Id` проходит через всю цепочку и возвращается в событиях;
- пути пишутся относительно сервиса, сервис определяется адресом в `servers`;
- авторизация — JWT (`Authorization: Bearer`), ошибки — RFC 7807 (`application/problem+json`)
  с полями `type`, `title`, `status`, `detail`, `instance` и `correlationId`;
- коды ответов у всех эндпоинтов: успех (`200` / `202`), `400`, `401`, `404`
  (зона, прибор или модель не найдены), `500` (внутренняя ошибка сервиса);
  где нужно — `403` (нет прав на зону), `409` (зона или прибор удалены),
  `422` (команда не входит в единую модель команд категории).

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
